Система работает медленно во многих сценариях, а самое важное - обрабатывает медленно заказы или вообще их теряет. В следствии чего пользователи не довольны и компания теряет деньги.

# Мотивация
Мониторинг нужен для того чтобы понять причины проблем, принять обоснованные решения по изменению системы, и следить за тенденциями - делаем ли мы ситуацию хуже или лучше со временем.
Это даст возможность:
- Быстро находить и устранять проблемы.
- Улучшение видимости и повышение безопасности системы.
- Повышение быстродействия системы и распределение ресурсов.
- Ускорение рабочего процесса и DevOps.
- Ценные бизнес-инсайты.
- Повышение удовлетворённости пользователей.

Своевременное решение проблем, которые связаны с производительностью и функциональностью приложения, улучшает пользовательский опыт.

#### Выбор подхода к мониторингу

Будем использовать подход RED - для сервисов, которые управляются запросами.

Для MES API (или по новой схеме - MES Calculator и MES Executor) будем использовать подход USE, их производительность снижается при интенсивном использовании.

#### Какие метрики будем отслеживать:
1. Number of dead-letter-exchange letters in RabbitMQ - показывает количество сообщений, которые были перенаправлены в dead-letter exchange. Важно отслеживать, чтобы понимать, сколько заказов "потерялось" и предпринять действия.
2. Number of message in flight in RabbitMQ - количества сообщений, которые в данный момент находятся "в полете", то есть между их получением (delivery) очередью и подтверждением (acknowledgement) их обработки потребителем. Если очередь постоянно растёт или уже достигло критичных значений, то стоит масштабировать сервис MES, чтобы обработка заявок не была слишком долгой и мы не начали их терять.
3. Number of requests (RPS) for internet shop API - частота запросов даёт представление о пропускной способности сервиса. Эта метрика может помочь избежать сбоев — будем отслеживать пиковый трафик и сможем прогнозировать, сколько нужно ресурсов.
4. Number of requests (RPS) for CRM API
5. Number of requests (RPS) for MES API
6. CPU % for MES API - среднее время, которое ресурс занят работой. Нужно следить за тем, чтобы сервису хватало ресурсов, иначе он будет деградировать по производительности. 
7. Memory Utilisation for MES API - процент использования оперативной памяти. Нужно следить за тем, чтобы сервису хватало ресурсов, иначе он будет деградировать по производительности. 
8. Response time (latency) for shop API - количество времени, которое уходит на выполнение одного запроса. Объективная информация про latency показывает скорость работы системы. Скорость работы системы напрямую влияет на удовлетворённость пользователей системой.
9. Response time (latency) for CRM API
10. Response time (latency) for MES API
11. Number of HTTP 500 for shop API - количество неудачных запросов в секунду. Неудачные запросы означают, что пользователь получил ошибку и не смог получить желаемое. В результате удовлетворённость пользователей системой падает.
12. Number of HTTP 500 for CRM API
13. Number of HTTP 500 for MES API

# План действий

1. Развернуть инстанс time-series базы данных (например, Prometheus) для хранения метрик.
2. Настроить сервер визуализации (например, Grafana) для построения графиков и дашбордов.
3. Организовать сбор метрик с API и бэкенд-сервисов. Использовать OpenTelemetry SDK.
4. Создать визуализацию в системе дашбордов Grafana.
5. Внедрить систему алертов - развернуть Alertmanager, интегрировать с уведомлениями: Email, Telegram и т.д.
