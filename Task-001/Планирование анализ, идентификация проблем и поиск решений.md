# Анализ схемы и описание системы
Нынешнее приложение состоит из трёх приложений:
* Онлайн-магазин — написан на Vue и Java Spring Boot.
* CRM — SPA-приложение, фронтэнд написан на Vue, бэкенд — на Java Spring Boot.
* MES — SPA-приложение, фронтенд написан на React, бэкенд — на C#.

# Существующие и потенциальные проблемные места
## Существующие проблемные места
* Клиенты жалуются, что над их изделием работают долго. Проблемы не на стороне производства.
* Представители компаний (пользователи API) сообщают, что не получают свои заказы.
* Жалобы от операторов: когда они заходят на первую страницу MES, система долго прогружается. 
* Низкий time-to-market. Задержки релизов при нахождении критичных проблем. 
* Недовольство клиентов онлайн-магазина (B2C)

## Потенциальные проблемные места:
* Каждое приложение имеет по одному инстансу.
* Базы данных имеют один инстанс, который работает на запись и на чтение.
* В CI/CD есть из проверок есть только юнит-тесты.
* MES занимается несколькими делами одновременно, тормозит и, возможно, теряет заказы.
* Использование разных технологий (veu-react, c#-java) мешает переиспользованию кода, а также не позволяет разработчикам свободно переходить с проекта на проект и подхватывать при необходимости разработку.
* Нет отслеживания прохождения заказов по статусам, нет единого места информации про состоянии заказа. Из-за этого может быть сложно следить за корректным и своевременным исполнением заказов
* Отсутствие авто-тестов. Замедляет time-to-market
* Игнорирование инициативы сотрудников по повышению качества. Странно, что уже есть несколько прототипов авто-тестов от QA, но нет самих работающих авто-тестов.
* Одного QA точно мало. Как минимум на один месяц в год сотрудник уходит в отпуск, а также может заболеть или уволится. В это время проект останется без тестирования вообще.
* Возможно, для поддержки приложения нужно использовать специальных людей, а не продакт-менеджера. Это будет эффективнее с точки зрения использования ресурсов и оперативности решения проблем.
* В release-окружения и продакшн версию деплоят вручную. Возможно, это снижает time-to-market.
* Отсутствие SLA и чёткого механизма оповещения клиентов о задержках
* Сервисы Shop API и CRM API работают с одной базой данных. Это не соответствует паттерну Database per service и может приводить к ошибкам.

# Что нужно сделать

* Систему позволяющую обрабатывать заказы клиентов магазина и других продавцов стабильно и без задержек. Базу данных которая имеет  возможность горизонтальное масштабирование для разделения запросов на чтение и запись.
* В систему необходимо добавить функции логирования и мониторинга, логирования, трейсинга и кэширования для обсервабилити и для принятия решений на основе актуальных данных.
* Создать службу поддержки
* Усилить отдел QA чтобы начать создавать автотесты
* Разделить MES сервис на две части отдельных сервиса: расчёт стоимости заказа и исполнение заказа. Сервис расчёта стоимости заказа можно масштабировать отдельно.
* Создать рассылку сообщений пользователям, если исполнение заказа выходит за обещанные сроки.
