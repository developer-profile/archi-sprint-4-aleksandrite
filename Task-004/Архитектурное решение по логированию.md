## Архитектурное решение по логированию

Для начала необходимо провести анализ текущей ситуации с заказами.

В связи с этим необходимо обеспечить логирование всех эндпоинтов и потребителей RabbitMQ. Логирование должно осуществляться на уровне INFO для фиксации начала и завершения выполнения эндпоинта или потребителя, а также на уровне ERROR для регистрации всех возникающих ошибок.

В логах следует фиксировать следующие данные: время выполнения, идентификатор покупателя, номер заказа, тип операции, а также информацию об ошибках и стек вызовов в случае их возникновения.

Рекомендуется также добавить логирование уровня WARNING для ошибок или исключений, которые могут быть частью нормального рабочего процесса.

Для сложных реализаций эндпоинтов, где существует риск затруднений в понимании пути выполнения кода, можно добавить логирование уровня DEBUG в вложенных блоках кода, таких как конструкции if, case или вызовы методов и функций.


Список статусов заказов, вокруг которых нужно добавить логирование по сервисам:
- shop-api
    - INITIATED:  Время изменения, ID пользователя, номер заказа, новый статус.
    - FILE_UPLOADED: Время загрузки, ID пользователя, тип файла, размер.
    - SUBMITTED: Время начала , ID пользователя, номер заказа, новый статус.
- mes-api:
    - PRICE_CALCULATED: Время расчета, ID пользователя, номер заказа, новая цена.
    - MANUFACTURING_STARTED: Время начала производства, ID пользователя, номер заказа.
    - MANUFACTURING_COMPLETED: Время завершения производства, ID пользователя, номер заказа.
    - PACKAGING: Время упаковки, ID пользователя, номер заказа.
    - SHIPPED: Время отгрузки, ID пользователя, номер заказа.
- crm-api:
    - MANUFACTURING_APPROVED: Время утверждения, ID пользователя, номер заказа.
    - CLOSED: Время закрытия, ID пользователя, номер заказа.
- other:
    - WARNING: Для нестандартных ситуаций, например, повторный расчет стоимости.
    - ERROR: Для сбоев, например, ошибка при подтверждении заказа.
    - DEBUG: Для отладки, например, детализация запросов к Shop API.

Передав идентификатор заказа в систему поиска логов, можно отслеживать всю историю его жизненного цикла. Это включает временные метки и все ошибки, возникшие при обработке.

## Мотивация

Логирование — это процесс записи информации о событиях, операциях и ошибках внутри системы. Оно играет ключевую роль в наблюдаемости системы, упрощает отладку, мониторинг и улучшает безопасность. Внедрение логирования помогает компании не только быстрее выявлять и устранять проблемы, но и оптимизировать бизнес-процессы, повышая эффективность работы.

Логирование необходимо для:
1. Отслеживания статусов заказов — помогает быстро выявлять и устранять проблемы на каждом этапе.
2. Анализа производительности — выявление узких мест в процессе производства и доставки.
3. Безопасности — обнаружение подозрительных действий (например, DDoS-атак или несанкционированного доступа).
4. Улучшения пользовательского опыта — анализ поведения клиентов для оптимизации интерфейса и процессов.
5. Поддержки аналитики — сбор данных для бизнес-метрик, таких как среднее время выполнения заказа, процент отмененных заказов и т.д.

Внедрение логирования, как и трейсинга, может повлиять на ключевые технические метрики: частоту запросов, длительность, утилизацию и количество ошибок.

Сначала стоит настроить логирование и трейсинг в сервисе mes-api. В этом сервисе есть длительные операции, такие как расчёт стоимости заказа, много логики с изменением статуса, а также консьюмер RabbitMQ, который может быть источником проблем.
Затем нужно настроить crm-api. В этом сервисе есть продьюсер RabbitMQ, который также может стать причиной проблем.
Асинхронные операции сложнее отследить, поэтому они требуют особого внимания при поиске проблем.
В поиске причины проблем поможет логирование.

## Предлагаемое решение

Технологии:
- ELK-stack (Elasticsearch, Logstash, Kibana) для сбора, хранения и визуализации логов.

Основные компоненты:
1. Агенты сбора логов на каждой системе (Fluentd/Filebeat).
2. Централизованное хранилище (Elasticsearch).
3. Визуализация и анализ (Kibana).

Новые связи на схеме:
- Все системы → Logstash/Fluentd → Elasticsearch → Kibana.

Политика безопасности:
- Чувствительные данные: Маскировка персональных данных (например, ID пользователя, токены, пароли и пр.) в логах.
- Доступ: Только для DevOps и аналитиков, разделение по необходимым ролям.

Политика хранения:
- Срок: 3 дня для детальных логов, 30 дней для агрегированных данных.
- Размер: Отдельные индексы под каждую систему.



## Превращение системы сбора логов в систему анализа логов

Анализ логов:
- Алертинг: Настройка уведомлений при резком росте ошибок или изменении статусов.
- Аномалии: Поиск необычных паттернов (например, массовое создание заказов).
- Тренды: Анализ изменений в поведении пользователей и производительности системы.
- Сравнение: Сравнение с предыдущими периодами для выявления изменений.
- Визуализация: Графики и дашборды для мониторинга ключевых метрик.

Нужны алерты для случаев:
- резкое увеличение общего количества логов
- резкое увеличение количества ERROR и WARNING
- резкое увеличение количества логов по конкретному статусу заказа
- резкое увеличение количества логов по конкретному пользователю
